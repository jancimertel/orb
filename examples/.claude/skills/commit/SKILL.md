# Making a commit

Invoke this behavior whenever the user asks for a commit. The goal is **one
logical change, one commit, one tight message** — not a dump of whatever is
dirty.

## Before writing the message

1. Run `git status` and `git diff` to see what's actually changed.
2. Run `git log -n 10 --oneline` to match the repo's existing style
   (conventional commits vs. plain subject, scope prefix, capitalization).

## Staging

- Stage only files that belong to the change the user described.
- Never `git add -A` / `git add .` — it sweeps in `.env`, credentials, build
  artifacts, and unrelated edits.
- If the diff spans multiple concerns, stop and ask the user how to split
  before committing.

## Message

- Subject ≤ 72 chars, imperative mood ("add X", not "added X" / "adds X").
- Body only if non-trivial; explain the **why**, not the what — the diff
  already shows the what.
- No trailing "🤖 generated by …" lines unless the repo's own history uses
  them.

## Hard rules

- Do **not** push after committing unless asked.
- Do **not** `--amend` an existing commit unless asked — create a new one.
- Do **not** pass `--no-verify` to bypass hooks. If a pre-commit hook fails,
  fix the underlying cause and create a **new** commit.

## Done

Report the resulting short SHA and subject line. Nothing else.
